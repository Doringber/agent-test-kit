# PRD-001: Cloud Infrastructure for Testing Stateful AI Agents

**Status:** Approved. Architecture derived in [ARCH-002](../architecture/ARCH-002.md).
**Date:** 2026-08-09

> **Layer 3 document.** Product context, not engineering instruction. Read this to understand *why* the system is shaped the way it is. Do not read it to decide what to build; that is [current-phase.md](../development/current-phase.md).

## 1. Vision

Software engineering has one durable rule: **you cannot ship what you cannot run repeatedly in a controlled environment.** Every era produced the infrastructure that made its dominant artifact runnable. CI made builds repeatable. Docker made environments repeatable. BrowserStack made browser matrices runnable. LocalStack made cloud services local.

AI agents are the first widely deployed software artifact for which no such infrastructure exists. An agent is a non-deterministic actor performing a distributed transaction across systems the developer does not own. Running it once is easy. Running it a thousand times, identically, without touching production, is currently impossible for essentially every team.

The consequence is not that agent testing is bad. **It is that agent testing largely does not happen.**

### Why now

- Tool-calling agents crossed from demo to deployment across 2024 to 2026.
- MCP emerged as a de facto interface standard. For the first time the boundary an agent crosses is enumerable and interceptable. **This is the enabling condition; before a standard tool interface this product was not buildable.**
- The industry converged on evaluating outputs and left verification of behavior almost entirely unaddressed.

### What changes in software engineering

1. **Determinism stops being free.** Every practice built on it (regression testing, bisection, bug reproduction, binary gates) must be rebuilt on statistical foundations.
2. **The unit of testing moves from output to trajectory.** What matters is the ordered sequence of actions taken against the world, and the state that world was left in.
3. **The test environment becomes the hard part.** In conventional software the code is complex and the environment is cheap. For agents the code under test is a prompt and a model, and the *environment* is the expensive, fragile, irreproducible component.

## 2. Product thesis

### Why traditional testing infrastructure fails

| Assumption | Why it breaks |
|---|---|
| Same input, same execution | False. Every run samples from a distribution |
| Pass or fail | Insufficient. The meaningful verdict is a rate |
| Static fixtures suffice | Insufficient. An agent creates, then reads back. A static fixture cannot answer a read that depends on a write the agent chose to make |
| The test knows what will be called | False. The agent decides at runtime |
| A failed run leaves no residue | False. It may have created three tickets and issued a refund |
| Execution is cheap | False. Tokens and 10 to 180 seconds per run |
| Reproducing means re-running | False. Requires replay of a recorded world |

### Why assertions are not the problem

Assertions are roughly three weeks of work. We know precisely, because the superseded `src/agent_test_kit/` implemented a competent assertion engine in about 460 lines. It was good, and it was not a company:

**Nobody was blocked on the assertion. They were blocked on having anything to assert against.**

The developer does not lack a way to express "read the invoice before refunding it". They lack a way to run that scenario a hundred times without a hundred real refunds. The assertion library is the steering wheel. We are building the road.

## 3. What the product is, and is not

**Is:** a hosted execution environment in which an agent runs repeatedly against a controlled, stateful, reproducible simulation of the external systems it depends on. Four capabilities: world capture, world simulation, statistical execution, reproduction.

**Is not:** an evaluation platform, an observability platform, a model gateway, an agent framework or runtime, a prompt management tool, a runtime authorization layer.

**Boundary:** starts when a developer points the recorder at an agent. Ends when a verdict with a replayable artifact reaches a pull request or CI job. **We do not cross into production.**

## 4. Core principles

Ten, each with its stated cost. A principle with no cost is a slogan.

1. **Reproducibility is the product.** *Cost:* rules out any feature introducing unrecorded non-determinism.
2. **The world is a first-class artifact**, versioned and reviewed like code. *Cost:* format investment before user-facing polish.
3. **Side effects are first-class**, not exceptions. *Cost:* we cannot ship a much easier read-only-first product.
4. **Statistical by default, binary by choice.** *Cost:* every surface is harder than the naive version.
5. **Local-first, cloud-scaled.** *Cost:* two execution paths kept behaviorally identical forever. The largest ongoing engineering tax in the plan.
6. **Infrastructure before dashboards.** *Cost:* the product demos poorly for months.
7. **Contracts before judges.** *Cost:* we forgo the most impressive demos in the category.
8. **The SDK is free forever and never crippled.** *Cost:* we must be genuinely good at infrastructure; we have no other leverage.
9. **Zero production coupling.** *Cost:* forgoes the runtime business, deliberately.
10. **Honest verdicts over green checkmarks.** *Cost:* we report more uncertainty than competitors and look worse in bake-offs.

## 5. Personas

| Role | Persona |
|---|---|
| **Installs** | Agent-owning backend engineer who owns one agent that writes to a system of record |
| **Champions** | Platform or AI enablement lead who fields write-access requests across teams |
| **Pays** | Engineering Manager or Director with tooling budget |
| **Blocks** | Security and infrastructure review. "Where does the recorded data live?" This objection is existential and is designed for from day one |
| **Indifferent** | ML research engineers. They have eval tooling and do not want this. We do not chase them |

## 6. Jobs to be done

1. When I change a prompt, know whether the agent still behaves correctly, before merge.
2. **Test an agent that writes to Jira without creating real Jira tickets.** Probably the true wedge.
3. Distinguish a real regression from the model being the model.
4. Replay an exact run and change one thing.
5. Not spend four days writing fake MCP servers.
6. Not have CI take ninety minutes or cost forty dollars.
7. Learn about a cost regression from CI, not the invoice.
8. Let a teammate run the full suite locally in five minutes.
9. Test turn seven without replaying turns one to six.
10. Hand compliance an artifact.

---

## 7. MVP

> **Record your agent's real interaction with its MCP servers once. Replay it forever, deterministically, in CI, with zero side effects.**

That sentence is the product. It changes a binary state: an agent that could not be tested in CI now can be. That is a discontinuity, not an improvement, and discontinuities get shared.

**Success criterion:** ten engineers outside the company record a world and run a replayed test in CI, unaided, within 30 minutes, and at least four are still running it 30 days later.

---

## 8. Roadmap objectives

| Version | Single objective |
|---|---|
| v0.1 | Prove deterministic stateful replay is possible and usable |
| v0.5 | Prove statistical verdicts change decisions |
| v1.0 | Become a required CI gate |
| v2.0 | Eliminate the recording prerequisite (synthetic worlds) |

Runtime authorization appears nowhere on this roadmap. It is a possible year-four adjacency and is not planned for, discussed with customers, or designed toward.

## 9. Things we refuse to build

LLM-as-judge evaluation. Prompt scoring. Hallucination detection. General observability. A production agent runtime. Runtime policy enforcement. Prompt management. Red teaming. Generic dashboards. Hosting real third-party SaaS instances. A model gateway. Anything requiring a change to the customer's production agent code. A marketplace. Automatic test generation in v0.1.

Each exclusion has a reason recorded in the founding decision set; the operative list for engineering is in [CLAUDE.md](../../CLAUDE.md#what-we-are-not-building).

---

## 10. North Star

> **Agent tests should run like unit tests: instantly, identically, a thousand times, without touching anything real.**

Internal metric: **percentage of a customer's agent test suite that runs deterministically in CI on every commit.** Today, for essentially everyone, that number is zero.

---

## 11. Load-bearing assumptions, unvalidated

Recorded here so they are not mistaken for findings.

1. Teams want to test agents today, rather than intending to later.
2. Enough teams run write-capable agents to constitute a bottom-up market.
3. Recording once is preferable to writing mocks, in the user's judgment.
4. Worlds do not rot faster than teams tolerate.
5. Teams act on statistical verdicts rather than ignoring them.
6. Security permits recordings of production-shaped interactions to exist.
7. MCP remains dominant long enough to matter.
8. Teams commit worlds, or accept an alternative storage model.
9. Parallel execution is a compelling reason to leave a free local tool.
10. The debugging experience is valuable enough to build.

**Assumptions 1, 3, and 4 are partially addressed by [Milestone 0](../development/milestone-0.md) measurements M4 and M8. The rest require customer evidence, not engineering.**
